# W301CN 抬腕服务器看板：扩展能力研究

研究日期：2026-10-22（Asia/Shanghai）。状态：可行性研究，尚未实现手表看板。

## 目标与当前边界

用户提供：初代 OnePlus Watch，固件 `W301CN_11_A.71`；配对随身 vivo X200 Pro（Android 16），使用 OPPO 健康。一加 9 留在家中作为服务器。

目标是抬腕直接显示专用状态页，亮屏时数据持续更新；普通通知、看板截图、需要手动打开音乐卡片均不能算目标已经完成。当前尚未取得日常手机的健康 App APK、表盘样本或蓝牙抓包，也没有在 A.71 上验证任何自定义数据写入。

**结论：值得先研究手机端协议和已有动态显示入口，暂不刷固件。没有找到可直接用于 W301CN A.71 的公开 SDK、通用自定义动态表盘工具或已复现服务器看板项目；这只是本次检索结果，不能证明这些能力绝对不存在。**

## 已确认的公开事实

| 事实 | 证据与适用范围 | 对目标的意义 |
|---|---|---|
| 初代使用 RTOS，官方描述 UI、传感器和蓝牙由多个芯片分工处理 | [一加官方 FAQ，2021-03-31](https://community.oneplus.com/thread/1411152) | 不能把 Wear OS 的 APK、Data Layer、Complication 示例直接套用 |
| 官方规格列出的连接是 BT5.0、BLE/BR/EDR | [初代官方规格](https://www.oneplus.com/global/watch/specs) | 手机到手表应先研究现有蓝牙连接，不假定只使用 BLE GATT，也没有依据承诺独立 Wi-Fi 联网 |
| 原厂支持抬腕亮屏、功能卡片、从健康 App 切换/添加表盘；天气表盘和天气卡片的数据由健康 App 获取并推送 | [原厂用户手册，1.6—1.8、2.6](https://service.oneplus.com/content/dam/support/user-manuals/common/OnePlus_Watch_User_Manual_EN.pdf) | 已有动态数据链路，但文档没有开放任意外部字段绑定或自定义渲染接口 |
| 官方允许选择照片作为表盘背景 | [一加官方 FAQ](https://community.oneplus.com/thread/1411152) | 能换背景不等于支持运行程序，反复上传整张图片也不是已验证的实时刷新机制 |
| 初代国际版 B.65 官方更新增加了实时导航显示、Spotify 播放列表同步，需要对应健康 App 版本 | [官方 B.65 更新公告，2021-09-02](https://community.oneplus.com/thread/1493039) | 导航通道是有依据的动态显示研究线索；国际版 B.65 不能证明国行 A.71 含相同命令、布局、权限或唤醒行为 |

历史旁证：xDrip 项目维护者在 2021-08-08 因初代 RTOS、缺少 SDK 和开发资源而关闭适配请求。[原始 Issue #1695](https://github.com/NightscoutFoundation/xDrip/issues/1695)。这说明当年的第三方开发困难，不能推导“2026 年仍绝对没有 SDK”。

原始个人实验记录：作者在 2021-05-17 描述了通过手机蓝牙工具传输 `B280STM32_ota.bin`，把初代国行转换为国际版。[作者实测文章](https://kagaminobouken.blog.jp/archives/43865644.html)。这是固件传输入口的历史线索，不证明 A.71 接受任意修改包、支持降级或能够恢复；不作为现在刷机的操作依据。

## 候选路线与尚未证明的前提

| 路线 | 判断 | 必须验证的前提 |
|---|---|---|
| 解码原厂表盘包，修改显示资源并绑定现有动态字段 | 首选研究方向；尚无本机样本 | 包是否只是静态资源、是否包含脚本/字节码、字段绑定表在哪里、资源更新如何校验、原布局能否稳定恢复 |
| 研究天气或导航数据通道，寻找小数据包更新界面的入口 | 有原厂动态显示依据，但只属于协议假设 | A.71 是否存在、能否承载任意字段、显示长度/频率、原厂 App 的配对状态和鉴权、能否抬腕直接进入且维持界面 |
| 利用媒体信息显示状态文本 | 仅适合低成本通信验证，不能预认定为目标方案 | 原厂界面是否显示并更新媒体信息、前后台恢复行为；即使成功，也不代表已获得默认表盘和专用布局 |
| 每几秒重传一张看板背景或整个表盘包 | 不作为默认实现 | 安装时间、是否中断显示、持久化写入行为和长期稳定性都未知；未证明可作为数据流接口 |
| 修改或替换手表固件 | 后置路线 | 匹配的固件样本、镜像结构、签名/加密/完整性验证、启动方式及实际可用的恢复手段 |

手机端增加桥接程序也不是天然可行：独立程序可能无法与原厂 App 同时占用协议连接；修改 APK 后的签名变化可能影响权限与数据。必须从实际 OPPO 健康版本分析，不能先承诺保留现有配对就能注入任意数据。

## 最小验证顺序

1. **取得只读样本。** 记录 vivo 的实际设备身份、健康 App 包名与版本；从已安装版本提取 APK（含 split APK）及哈希。表盘缓存只有在本机正常权限允许读取或 App 可导出时获取，不把 Android 私有目录假定为可直接读取。当前这些材料尚未取得。
2. **离线定位模块。** 从 APK 内搜索 W301/B280 型号分支、表盘与天气/导航模块、蓝牙传输、命令定义和校验。只在对应初代分支发现实现才列为候选；不因 App 同时支持新款就误判旧表支持。
3. **观察原厂操作。** 对正常天气同步、切换表盘、导航和媒体控制分别采样；如需蓝牙 HCI 日志，仅保留短时、与实验相关的本地记录。导航若在 A.71 或该配套 App 中不存在，明确标为不适用，不以国际版公告补足证据。
4. **先证明可更新一个真实字段。** 在可恢复的既有接口中实现两次可辨识更新，确认字段、数据包和刷新对应关系。测试文字与天气占位值只能证明通信，不作为最终看板。
5. **再证明体验成立。** 多次抬腕无需滑动即进入选定页面，亮屏期间持续刷新；熄屏、重连、手机后台、服务断线和恢复后仍行为一致。仅“通过蓝牙发送成功”不满足验收。

建议首次约定亮屏刷新目标为 2—5 秒，作为待测性能目标而非设备能力声明。服务端始终携带观测时间、有效性与序号；旧缓存不得重新加盖当前时间。不可达、缺失和过期数据必须显示“未知/已过期”，不能继续显示绿色正常。抬腕首次画面可以先显示明确标注时间的缓存，再显示新数据，具体时效由实际链路测量决定。

## 决策门槛

- 若资源包可定制且可小包更新变量，推进“原厂表盘格式 + 手机桥接”。
- 若只能复用天气/导航的固定布局，先评估能否满足专用页面要求；不把借用字段的演示当成完整交付。
- 若所有可见入口只能换背景或发通知，当前固件就没有已验证的实现路线。此时才评估固件研究的收益、恢复条件和投入，不承诺靠反编译自动生成可编译的原厂源码。

本次研究没有执行配对变更、固件写入、App 替换、实际自定义协议发送或设备端看板安装。

## 本地准备与下一步

电脑当前尚未发现 vivo 的已授权调试连接。因此下一阶段缺的是实际安装版本的 APK，而不是服务器采集代码。

已准备只读工具 [`tools/collect_watch_companion.ps1`](../tools/collect_watch_companion.ps1)。连接 vivo 并完成 USB 调试授权后，先用 `adb devices -l` 确定 vivo 序列号，再执行：

```powershell
.\tools\collect_watch_companion.ps1 -Serial '<vivo序列号>'
```

默认包名为候选 `com.heytap.health`，并非已经在本机确认；如果不匹配，应查明真实包名后通过 `-PackageName` 指定。工具强制选择设备、校验 vivo 厂商，拒绝项目中的一加 9 服务器标识；只复制已安装 APK 与 split APK、版本信息及 SHA-256，不采集健康数据库、账户数据或蓝牙日志。输出保存在 Git 忽略的 `artifacts/watch-w301cn/<时间与随机后缀>/`。

已完成 PowerShell 语法检查与服务器设备拒绝检查；没有 vivo 真机连接，APK 提取与后续协议分析尚未运行验证。蓝牙日志如后续确有需要，再按最小实验范围单独获取。AOSP 提供了 [HCI 日志分析说明](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging)，但 vivo Android 16 的日志可访问性仍须本机确认，不能预设非 Root 情况下能直接读取系统日志目录。
